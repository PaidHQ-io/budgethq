45. **Pacing-aware handling of lumpy/contracted spend** — `computePacing`'s projection (`projectPlatformSegment`) assumes a roughly steady daily rate: spend-to-date ÷ days-elapsed × total-days. Flighted campaigns, seasonal spikes (BFCM, holidays), and lump-sum contracted buys (sponsorships, prepaid IOs paid once but running for months) all break that assumption — a segment can read as wildly "ahead of pace" or "behind pace" for reasons that have nothing to do with real pacing risk. There's a second, related gap Mo raised directly: the full-period model is a cumulative average, so a budget change made yesterday is diluted by every prior day of the period and barely moves the projection for weeks. **Multi-model forecast picker shipped 2026-07-24** — `budgetRowMeta[segKey]._forecastModel` (string enum, replacing the earlier single `_committed` boolean, which is still read as a fallback for rows toggled before this shipped) selectable per segment from a picker **in the Reporting & Pacing tab's segment table** (moved there 2026-07-24, per Mo — it started in the Budget Panel but choosing HOW a segment's spend is projected is a pacing decision, not a budget-setup one; the Budget Panel only keeps `_notBudgeted`, which genuinely is a budget-setup flag). Same underscore-prefixed-key `budgetRowMeta` pattern as `_notBudgeted`: `"full-period"` (default, unchanged cumulative average), `"committed"` (lump-sum bypass — `projected = max(spend, budget)`, reports the existing `"committed"` status), and `"trailing1"`/`"trailing3"`/`"trailing7"`/`"trailing14"`/`"trailing30"` (N-day trailing average of each platform's daily spend, clamped to the days actually elapsed so a fresh window ramps up gracefully instead of requiring a full N days of history first — `projectPlatformSegment` parses N straight out of the model string via regex rather than hardcoding each value, so adding another window doesn't need a matching code change). trailing1/trailing3 added 2026-07-25 per Mo — even trailing7 dilutes a budget shift made a couple days ago across 5+ days of the old rate before it moves the projection much; trailing1 ("yesterday's rate") reacts instantly at the cost of being noisy (a single low-spend day, e.g. a weekend, swings the whole number), trailing3 is a middle ground. Threaded through `computePacing` → Dashboard, Ask AI (`query_pacing`), the AI Summary card, and every export/report, same as the original committed flag. **Day-of-week seasonality shipped 2026-07-25**, per Mo's push for BudgetHQ to build a genuine forecasting moat instead of the flat/linear pacing every competitor does — `computePlatformDayOfWeekIndex` learns each platform's typical weekly shape (e.g. Sundays run 70% below that platform's average day) from ALL of a workspace's history, clamped and requiring a minimum sample size per weekday before it's trusted. `projectPlatformSegment` now deseasonalizes every known day in its estimation window before averaging, then reseasonalizes across the full period day-by-day — this is what fixes trailing1/trailing3's biggest weakness (a quiet Sunday no longer reads as "spend crashed"). Applies automatically to every model (full-period and every trailingN), not a separate pickable option — with no historical weekday data yet, indexes default to neutral (1.0 for every day), which reduces mathematically to the exact old flat-average behavior, so this is a strict accuracy improvement rather than a new mode. Platform-level, not per-segment, since most individual segments won't have enough history yet to learn their own weekly shape reliably. Considered and explicitly ruled out for now: SARIMAX/Prophet (Python-native, need a separate service plus far more historical data per segment than most workspaces have yet — real risk of confidently-wrong numbers on sparse data) and Marketing Mix Modeling (an attribution technique that needs an outcome variable like revenue/conversions to regress against — BudgetHQ is spend-only today, so there's nothing for MMM to model). **Capacity-vs-budget signal shipped 2026-07-25** — the other half of "why is this segment behind pace": `detectCapacitySignal` (in `computePacing`) finally puts `spend_rows`' impressions column to use (collected since the schema's earliest version, never read until now). For a segment that's genuinely behind pace AND has real budget headroom left, it compares the last 7 days of impressions against the 7 days before that; if impressions haven't grown at least 15%, it flags `capacitySignal:"constrained"` — a candidate read of "more budget alone won't fix this, delivery is capped by audience size/frequency cap/the platform's own bid or approval limits, not by dollars." Requires impressions specifically (not spend) to be flat, since spend alone plateauing while impressions keep climbing usually just means costs changed, not that delivery hit a ceiling. Surfaced as a small warning badge next to the Status pill in the Reporting & Pacing tab (only shown for the "constrained" case — "growing" and null are both non-findings), plus a `segments_capacity_constrained` count in Ask AI's `query_pacing` tool. Heuristic, not a verdict — a known limitation is it only counts calendar days that have at least one spend row, so a paused campaign (zero rows, not zero-valued rows) silently shrinks its comparison window rather than counting as a real dip. Related to but distinct from "Forecasting / scenario modeling" below — that's user-driven what-if planning; this is the existing automatic projection being wrong for non-steady spend, independent of any scenario tooling. **Global default forecast model shipped 2026-07-25**, per Mo — "there should be a global forecasting model selector instead of just individual rows. the individual row selector should override the global." `defaultForecastModel` is a new top-level workspace setting (persisted via the same debounced save as `savedViews`, new `default_forecast_model` column, defaults to `"full-period"`) set from a dropdown in the Reporting & Pacing tab's Budget-view filter bar. `computePacing`'s fallback chain is now per-row `_forecastModel` override → legacy `_committed` boolean → workspace `defaultForecastModel` → `"full-period"` last resort, threaded through every `computePacing` call site (Dashboard, Budget Panel export preview, Ask AI's `query_pacing`/summary tools, all four report builders). The per-row picker's first option is now an explicit "Use global default (X)" (`FORECAST_MODEL_INHERIT` sentinel, stored as simply no `_forecastModel` key — same underlying mechanism as before, just reachable as its own menu item instead of silently meaning `"full-period"`) so picking anything else is a real, visibly-highlighted per-row override rather than a specific model being conflated with "unset." **Redesigned into Auto/Manual/Committed shipped 2026-07-25**, per Mo: "we have too many [models] and I don't understand them ... the point is accurate forecasting, not overly complex options." The 7-option list (full-period/committed/trailing1/3/7/14/30) is gone from the UI, replaced with 3 real choices — Auto (new default, replaces full-period), Committed (unchanged), and Manual (replaces the 5 fixed trailing presets with one free-form "trailing N days" number input, stored the same way the presets always were, `"trailingN"`). Auto is a genuinely adaptive algorithm, not just a rename of the old flat cumulative-average: `projectPlatformSegment` now blends a full-period ("long-run") deseasonalized rate with a short 7-day one, weighted by how much they've diverged (`computeAutoBlendWeight` — under 15% relative divergence, pure long-run; over 50%, pure recent; linear ramp between). This directly fixes full-period's core weakness (a budget change made yesterday used to be diluted by every prior day of the period and barely moved the projection for weeks) without Manual's tradeoff of needing a human to pick and tune a window size, and without a short window's noise problem when nothing's actually changed. The legacy `"full-period"` string is still recognized (for configs saved before this shipped) but is no longer offered as a choice anywhere, so old data doesn't silently change behavior. `computeCustomGrouping` (which never passed a `forecastModel`) now gets Auto by default too, a deliberate accuracy upgrade for Custom-view groupings. Verified numerically (not just by inspection) with a standalone script exercising `projectPlatformSegment` against synthetic steady/spiking/mildly-diverging spend series before shipping — confirmed Auto matches full-period exactly on steady spend, matches a pure trailing-7 rate on a sharp recent spike (divergence far past the 50% cutoff), and matches the long-run rate on a mild divergence within the no-blend zone. Also added, per Mo's request: an in-app "ℹ️" explanation (new `InfoTip` component in `shared.jsx`, next to the global control) walking through the actual forecasting plumbing — per-platform independent projection, day-of-week deseasonalization, then what each of the 3 models does — so the logic isn't a black box.
